# agents-mcp

Русский | [English](README_EN.md)

MCP-сервер платформы специализированных LLM-агентов. Каждый агент — папка
`agents/<name>/` с `prompt.md` и `config.toml`; добавление нового агента не
требует пересборки сервиса. В репозитории — только сам движок: агентов вы
пишете сами (формат — в разделе [«Добавление нового агента»](#добавление-нового-агента)).

## Возможности

- **MCP-инструменты**: вызов агентов — `invoke_agent`, `agent_run` (пуск в фон
  без ожидания), `wait_agent`, `agent_cancel`, `chain_cancel` (остановка всей
  цепочки работ по задаче); сведения — `list_agents`,
  `get_agent_info`, `agent_history`, `health`; управление службой —
  `config_reload`, `prepare_shutdown`; доска задач — `task_create`, `task_get`,
  `task_set_status`, `artifact_write`, `artifact_read`, `event_append`;
  файловые — `fs_read_file`, `fs_write_file`, `fs_edit_file`, `fs_mkdir`,
  `fs_list_dir`; навыки — `skill_load`.
- **Вызов без ожидания** — `agent_run`: пуск возвращает `call_id` и путь
  файла-итога сразу, проверка по `call_id` отвечает мгновенно. Ни один из двух
  режимов не держит вызывающего, поэтому клиенту не нужен скрипт-посредник.
- **Отмена фонового вызова** — `agent_cancel`: строка вызова закрывается
  ошибкой, файл-итог дописывается, ждущий не зависает.
- **Остановка цепочки работ** — `chain_cancel(task_id)`: отменяет все живые
  фоновые вызовы задачи и помечает саму задачу `cancelled` (ответ перечисляет
  отменённые `call_id`; закрытая задача — `already_closed`, неизвестная —
  `not_found`). Так останавливают цепочку `scripts/code_chain.py`: её скрипт сам
  видит статус `cancelled`, дописывает `result.json` со статусом `cancelled` и
  завершается кодом 4 — снимать процессы Windows больше не нужно.
- **Поставщики моделей**: прямые HTTP-подключения через
  `[providers.direct.<имя>]` бывают OpenAI-совместимыми (`api = "openai"`, это
  значение по умолчанию) и Anthropic Messages (`api = "anthropic"`, включая
  MCP-инструменты); Claude через Claude Code CLI (`claude -p`, со своими
  инструментами и MCP); OpenAI через Codex CLI. Плюс `mock` для тестов.
- **Два способа связи с клиентом**: Streamable HTTP (по умолчанию, без
  состояния сессии — нет «404 Session not found» после перезапуска) и
  стандартный ввод/вывод (`--transport stdio`) для клиентов, не умеющих HTTP.
  Набор инструментов одинаков.
- **Инструменты агенту — от обоих видов MCP-серверов**: и от тех, что живут по
  HTTP, и от тех, что запускаются процессом (`command` в `mcp_config`).
- **Перечитка без перезапуска**: каталог агентов подхватывается наблюдателем
  (задержка 500 мс), главный конфиг — наблюдателем или инструментом
  `config_reload`.
- **Кеш ответов** в хранилище (ключ sha256, срок жизни задаётся агенту).
- **История вызовов** в хранилище — метрики, трассировка, экземпляр службы.
- **Журнал службы** — отдельный файл SQLite `<log_dir>/agents-mcp.logs.db`
  (таблица `events`, поля события сжаты zstd), хранится 30 дней. Работает и при
  недоступной основной базе. Текстовых журналов нет. `RUST_LOG` задаёт общий
  уровень, но шумные библиотеки (`hyper`, `h2`, `axum`, `tower_http`, `tower`,
  `rmcp`, `tokio_util`) остаются на `warn`, пока не названы в `RUST_LOG` явно
  (например `rmcp=debug`).
- **Хранилище на выбор**: встроенный SQLite по умолчанию — служба стартует без
  внешней базы, файл создаётся сам; PostgreSQL — по указанному адресу
  (раздел [«Хранилище»](#хранилище)).
- **Один экземпляр на `log_dir`**: PID-замок с проверкой имени процесса.
- **Корректная остановка** по Ctrl+C/Break/Close/Shutdown (Windows) и SIGTERM
  (Unix); перед остановкой — `prepare_shutdown`, чтобы не оборвать идущие вызовы.

## Хранилище

Всё основное состояние службы (доска задач, журнал вызовов, ходы прогонов, кеш
ответов) лежит в одном хранилище. Журнал службы пишется отдельно — в файл
`<log_dir>/agents-mcp.logs.db`, поэтому отказ основной базы его не теряет.
По умолчанию это **встроенный SQLite**: внешняя база не нужна, файл базы и схема
создаются сами при первом запуске. Если задать адрес PostgreSQL в
`[storage].task_store_dsn` (лучше — переменной окружения
`AGENTS_MCP_TASK_STORE_DSN`, она перекрывает конфиг), служба работает на нём.

| Адрес | Что выбирается |
|---|---|
| не задан или пуст | встроенный SQLite по `[storage].sqlite_path` |
| `sqlite://путь` | встроенный SQLite по указанному пути |
| `postgres://…`, `postgresql://…` или `host=… user=…` | PostgreSQL |
| любая другая схема | ошибка запуска; в тексте ошибки — только схема, пароль из адреса не попадает |

**SQLite** настраивать не нужно: схема применяется при каждом открытии, повторный
запуск безопасен, режим журнала — WAL.

**PostgreSQL**: схему служба сама не создаёт — примените файлы `migrations_pg/`
по порядку (001–006), они идемпотентны. Пароль держите в переменной окружения, а
не в конфиге. Размер пула — `[storage].task_store_pool` (по умолчанию 8). При
старте служба закрывает ошибкой только свои повисшие вызовы — по экземпляру в
`agent_calls.instance` (`[server] instance`, по умолчанию «имя машины:порт»),
поэтому у нескольких служб на одной базе экземпляры обязаны различаться. На уже
работающей базе примените недостающие миграции до установки новой сборки
(`005` — экземпляр службы, `006` — путь файла-итога): без этих колонок запись
вызова упадёт.

Своя база подключается реализацией типажа `Store` (`src/store/mod.rs`) и веткой
разбора адреса в `parse_backend`/`connect`; образец — `src/store/sqlite.rs`.

## Раскладка на машине (пример)

```
C:\agents-mcp\
├── bin\agents-mcp.exe          # бинарник
├── configs\agents-mcp.toml     # передаётся ключом --config или переменной AGENTS_MCP_CONFIG
├── agents\                     # ваши агенты (подхватываются на ходу)
├── data\agents-mcp.sqlite      # встроенный SQLite: доска, вызовы, кеш
├── logs\agents-mcp.logs.db     # журнал службы (events), отдельно от основной базы
├── logs\agents-mcp.pid         # PID-замок
└── runs\                       # файлы-итоги фоновых вызовов agent_run
```

Относительные пути в конфиге (`sqlite_path`, `log_dir`, `runs_dir`,
`agents_dir`) отсчитываются от каталога самого файла конфига — отсюда `../` в
образце.

## Конфиденциальность

Запуск агента отправляет данные стороннему поставщику модели. Изоляции по
умолчанию нет, поэтому режим работы выбирает тот, кто разворачивает службу.

К поставщику уходят:

- текст задания (поле `input`) и системный промпт агента целиком;
- содержимое файлов, прочитанных файловыми инструментами;
- ответы ВСЕХ MCP-инструментов, выданных агенту: выборки из базы, куски кода,
  пути, имена объектов;
- рабочие пути в аргументах вызовов.

Поставщик хранит и использует полученное по своим правилам — служба на это не
влияет.

Безопасный режим по шагам:

1. Работать на изолированной копии репозитория, а не на рабочем каталоге:
   `git worktree` даёт копию только из файлов под контролем версий — без `.env`
   и других файлов вне git (секреты, зафиксированные в репозитории, в копию
   попадут). Правки возвращаются диффом и накладываются вручную.
2. Если агенту выдан поиск по коду — поднять для копии свой экземпляр индекса
   кода. Общий индекс знает все проекты машины и перечисляет их с путями, и это
   тоже уходит модели.
3. Взять копию рабочей базы, а не боевую, и учётную запись только на чтение.
4. Ограничить `[fs].allowed_roots` каталогом копии.
5. Сузить `allowed_tools` агента: каждый лишний инструмент — канал утечки.
6. Завести отдельный ключ поставщика со своим счётом и квотой. Предпочитать
   поставщика с договором о неиспользовании данных для обучения либо локальную
   модель через `[providers.direct.<имя>]`.

Шаги 1 и 2 вместе делает образец `scripts/clean_copy.py` — для индекса кода
[code-index](https://github.com/Regsorm/code-index-mcp) (`bsl-indexer`):

```bash
python scripts/clean_copy.py prepare <проект> <имя-копии> [--language python]
python scripts/clean_copy.py apply   <проект> <имя-копии>
python scripts/clean_copy.py remove  <проект> <имя-копии>
```

`prepare` создаёт копию в `<AGENT_WORK_DIR>/<имя-копии>` (по умолчанию
`C:/Temp/agent-work`, под Linux — `agent-work` во временном каталоге системы),
поднимает на `127.0.0.1:8037` индекс ровно по ней под
алиасом `work` и проверяет, что в ответах индекса нет чужих путей (если
конфиги общего индекса не найдены, скрипт предупреждает, что проверка
неполная). Индексатор
берётся из переменной `CODE_INDEX_EXE`, иначе `bsl-indexer` ищется в PATH;
конфиги общего индекса для проверки изоляции — из `CODE_INDEX_MAIN_HOME`
(по умолчанию каталог индексатора). `apply` переносит правки копии в проект без
фиксации, `remove` останавливает индекс и удаляет копию.

Локально остаются только файл-итог вызова, журнал службы и база вызовов.

## Установка

### 1. Сборка

```bash
cd <каталог репозитория>
cargo build --release
```

Бинарник: `target/release/agents-mcp.exe`. На Windows со средствами gnu-сборки
нужен `dlltool` в PATH (например, из w64devkit).

**Linux** (проверено на Ubuntu 22.04, x86-64): та же команда даёт
`target/release/agents-mcp`; с Windows-машины собирается `cargo zigbuild --release
--target x86_64-unknown-linux-gnu`. Нужен glibc не ниже 2.30. Пути в конфиге
(`sqlite_path`, `log_dir`, `runs_dir`, `agents_dir`, `[fs].allowed_roots`) под
Linux задавайте явно: без них `logs`, `runs` и `agents-mcp.db` ложатся в
текущий каталог процесса, а файловые инструменты разрешены в `/tmp`. Служба
корректно останавливается по SIGTERM и подходит для юнита systemd.

### 2. Раскладка

```powershell
$repo = "<каталог репозитория>"
$dst  = "C:\agents-mcp"
New-Item -ItemType Directory -Force -Path "$dst\bin", "$dst\configs", "$dst\agents" | Out-Null
Copy-Item "$repo\target\release\agents-mcp.exe" -Destination "$dst\bin\" -Force
Copy-Item "$repo\configs\agents-mcp.example.toml" -Destination "$dst\configs\agents-mcp.toml" -Force
```

Затем впишите в `configs\agents-mcp.toml` свои значения: пути к Claude Code CLI и
Codex CLI (или удалите их секции), `[fs].allowed_roots`.

### 3. Ключ и вход

Ключ DeepSeek — в переменной окружения, имя которой задано в `api_key_env`:

```powershell
[System.Environment]::SetEnvironmentVariable('DEEPSEEK_API_KEY', '<ваш-ключ>', 'User')
```

Вместо переменных пользователя можно положить файл `.env` в рабочий каталог
службы: он читается при старте и перечитывается вместе с конфигом.

Claude Code CLI и Codex CLI ключа не требуют — они авторизуются своим входом:
команда `/login` в Claude Code и `codex login` в Codex CLI.

### 4. Запуск

```powershell
C:\agents-mcp\bin\agents-mcp.exe --config C:\agents-mcp\configs\agents-mcp.toml
```

Служба слушает `http://127.0.0.1:8025/mcp`. Для клиента, не умеющего HTTP, —
`--transport stdio`. Запускать её в фоне можно любым диспетчером служб.

## Проверка и журнал

```powershell
# Проверка здоровья (без MCP-рукопожатия)
curl http://127.0.0.1:8025/health

# Лента событий журнала службы (последние 20 записей)
# Уровни в колонке level: 4 — error, 3 — warn, 2 — info.
sqlite3 C:\agents-mcp\logs\agents-mcp.logs.db `
  "SELECT datetime(ts/1000,'unixepoch'), level, target, message FROM events ORDER BY id DESC LIMIT 20"

# История вызовов агентов
sqlite3 C:\agents-mcp\data\agents-mcp.sqlite `
  "SELECT id, agent_name, provider, cost_usd, latency_ms, datetime(created_at, 'unixepoch') FROM agent_calls ORDER BY id DESC LIMIT 20"
```

## Конфиг

Полный образец с пояснениями —
[configs/agents-mcp.example.toml](configs/agents-mcp.example.toml). Минимум:

```toml
[server]
host = "127.0.0.1"
port = 8025
allowed_hosts = ["localhost", "127.0.0.1", "::1"]
# instance = "agents-mcp-1"  # по умолчанию «имя машины:порт»; у служб на общей базе — разный

[storage]
sqlite_path = "../data/agents-mcp.sqlite"  # встроенный SQLite (по умолчанию)
log_dir = "../logs"
runs_dir = "../runs"  # файлы-итоги фоновых вызовов agent_run
# task_store_dsn = "postgres://user:pass@db-host:5432/agents"  # задайте, чтобы работать на PostgreSQL

[agents]
agents_dir = "../agents"
hot_reload = true

[providers.direct.deepseek]
api_key_env = "DEEPSEEK_API_KEY"
base_url = "https://api.deepseek.com/v1"

[providers.direct.deepseek.prices."deepseek-flash"]
input = 0.3
output = 1.2
cache_read = 0.006

[providers.direct.anthropic-example]
api = "anthropic"
api_key_env = "ANTHROPIC_EXAMPLE_API_KEY"
base_url = "https://api.example.com/anthropic"
prompt_cache = true

[providers.claude_cli]
executable = "C:/Users/<пользователь>/.local/bin/claude.exe"
max_concurrent = 2
default_max_turns = 8

[providers.codex_cli]
executable = "codex"
codex_home = "C:/Users/<пользователь>/.codex"
max_concurrent = 2
```

У прямых HTTP-провайдеров `proxy` принимает адрес только со схемой `http` или
`https`, а `proxy_bypass` дополняет обязательный обход петлевых адресов и частных
сетей. У `codex-cli` эти поля работают иначе: `proxy` без проверки копируется в
`HTTP_PROXY`/`HTTPS_PROXY` запускаемого процесса, а `proxy_bypass` — в `NO_PROXY`
только вместе с `proxy`; автоматического обхода локальных сетей нет. У
`claude-cli` полей `proxy` и `proxy_bypass` нет, процесс наследует сетевые
переменные окружения службы.

Цены задаются отдельно для каждой модели HTTP-провайдера секцией
`[providers.<…>.prices."<модель>"]`; имя модели должно точно совпадать с
`model` в конфиге агента. `input` и `output` обязательны, `cache_read` и
`cache_write` необязательны; все значения — доллары за миллион токенов. Для не
заданной цены кеша применяется `input`. Стоимость из ответа поставщика
(OpenRouter `usage.cost` или Claude CLI) имеет приоритет. Если поставщик цену не
сообщил и модель не описана в конфиге, `cost_usd` равен `null`, без
предупреждения; токены при этом сохраняются. Изменения цен подхватываются при
перечитке главного конфига.

### Перекрытия настроек вызова (`overrides`)

`invoke_agent` и режим пуска `agent_run` принимают необязательный плоский объект
`overrides`. Он действует только на один вызов, не попадает в `input` и не
наследуется вложенными вызовами. Разрешён закрытый список ключей:

| Ключ | Значение и проверка |
|---|---|
| `model.name` | Непустая строка; провайдер не меняется |
| `model.temperature` | Число от 0 до 2 |
| `model.max_tokens` | Целое число больше 0 |
| `execution.max_turns` | Целое число больше 0 |
| `limits.timeout_sec` | Целое число больше 0 |
| `effort` | Непустая строка; заменяет уже заданное усилие провайдера |
| `cache.enabled` | Логическое значение |
| `mcp.<сервер>.url` | Адрес уже объявленного у агента MCP-сервера |

Неизвестный ключ, неверный тип, неизвестный сервер или запрещённый адрес дают
отказ вызова. Старшинство настроек: глобальный `force_provider`/`force_model`,
затем `overrides`, затем `config.toml` агента. Если параметр
`allowed_mcp_urls` секции `[agents]` непуст, адрес должен точно входить в этот
список; без списка разрешены только адреса `http://127.0.0.1:<порт>/mcp`.

```json
{
  "agent": "code-planner",
  "input": {"task": "Составить план", "work_dir": "C:/Project"},
  "overrides": {
    "execution.max_turns": 60,
    "mcp.code-index.url": "http://127.0.0.1:8037/mcp"
  }
}
```

Для цепочки тот же адрес можно передать коротким ключом:

```powershell
python scripts/code_chain.py --work-dir C:/Project --task "Исправить дефект" --code-index-url http://127.0.0.1:8037/mcp
```

### Секреты в настройках

Ключи HTTP-провайдеров по-прежнему задаются именем переменной в `api_key_env`.
В строках настроек можно использовать `${ИМЯ}` или
`${ИМЯ:-значение по умолчанию}`. Подстановка работает в `mcp_config` для `url`,
значений `headers`, значений `env`, элементов `args` и `command`, а также в
`proxy` HTTP-провайдеров. Например:
`"Authorization": "Bearer ${MY_TOKEN}"`. Значение берётся сначала из окружения
процесса, затем из первого найденного `.env`; пустая переменная использует
указанное значение по умолчанию. Если обязательной переменной нет, вызов агента
отклоняется, а HTTP-провайдер с таким `proxy` не регистрируется.

В секциях `[providers.direct.<имя>]` поле `api` выбирает договор API:
`"openai"` (по умолчанию) или `"anthropic"`. Для Anthropic `base_url`
указывается без `/v1`: путь `/v1/messages` добавляется автоматически;
`prompt_cache = true` помечает системный промпт и последний инструмент для
эфемерного кэша. У этого вида API нет живой записи потока через
`AGENTS_MCP_STREAM_DIR`, вытеснения старых результатов из истории через
`AGENTS_MCP_HISTORY_TRIM_AT` и возврата навыка модели при зацикливании потока.

### Переменные окружения

При старте служба ищет первый файл `.env` от текущего каталога вверх. Переменные
окружения процесса главнее одноимённых значений `.env`. Значения из `.env`,
которых нет в окружении процесса, при старте копируются в него.

Перечитка конфига (`config_reload` или сохранение файла конфига) перечитывает и
`.env`, но только в собственную карту службы — окружение процесса не меняется.
Новые, изменённые и удалённые значения сразу действуют для ключей из
`api_key_env` и для подстановок `${ИМЯ}` в `mcp_config` и `proxy`. Остальные
переменные из списка ниже служба читает из окружения процесса: для них значения
`.env` берутся на момент старта, а правки файла действуют только после
перезапуска.
Ошибка отдельной записи `.env` сообщается с номером строки, без её текста.

- `AGENTS_MCP_CONFIG` — путь к главному конфигу, если не передан `--config`.
- `AGENTS_MCP_TASK_STORE_DSN` — непустое значение переопределяет
  `[storage].task_store_dsn`.
- Имя из `api_key_env` каждого прямого провайдера — его API-ключ; без непустого
  значения провайдер не регистрируется.
- `RUST_LOG` — фильтр журнала `tracing`.
- `AGENTS_MCP_STREAM_DIR` — включает потоковый режим запросов прямых
  OpenAI-совместимых провайдеров и задаёт каталог живой записи потока: на каждый
  вызов пара файлов `<время_мс>-<модель>.stream.bsl` и `.raw.jsonl`, записи старше
  7 дней удаляются.
- `AGENTS_MCP_HISTORY_TRIM_AT` — доля окна контекста, после которой провайдер
  вытесняет старую историю; по умолчанию `0.6`, ноль или отрицательное значение
  отключает вытеснение, ошибочное значение заменяется значением по умолчанию.
- Для `claude-cli` путь профиля берётся из `config_dir`, а при его отсутствии —
  из `CLAUDE_CONFIG_DIR`. Долгоживущий токен ищется сначала в
  `CLAUDE_CODE_OAUTH_TOKEN`, затем в файле из `CLAUDE_OAUTH_TOKEN_FILE`; если их
  нет, файл `.claude/.credentials.json` ищется в `USERPROFILE`, затем в `HOME`.

`AGENTS_MCP_TRANSCRIPT=1` распознаётся провайдером, но в штатной службе сейчас
ничего не меняет: runtime всегда передаёт канал, который включает запись ходов.
Переменная действует только при отдельном вызове провайдера без этого канала.

### Перечитка без перезапуска

Главный конфиг перечитывается на ходу, без перезапуска службы. Запустить
перечитку можно двумя способами: сохранить файл конфига (при `hot_reload = true`
его подхватывает наблюдатель) или вызвать MCP-инструмент `config_reload`.

Применяются на лету: `[storage] runs_dir`; `[agents]` `force_provider` /
`force_model`, `default_timeout_sec`, `agents_dir` и `hot_reload`; весь `[providers.*]` (провайдер с
неизменившимися настройками остаётся тем же — со своими соединениями и
семафором); `[skills]` `rag_query_url`; `[fs] allowed_roots`.

Требуют перезапуска и приходят в ответе списком `restart_required`: весь
`[server]` (host, port, allowed_hosts, instance) и `[storage]` `log_dir`,
`sqlite_path`, адрес внешней базы (`task_store_dsn`) и `task_store_pool`.

Файл `.env` перечитывается вместе с конфигом; что из него применяется на ходу,
описано в разделе [«Переменные окружения»](#переменные-окружения). Идущие вызовы доживают на
прежнем наборе провайдеров, новые берут новый. Конфиг с ошибкой разбора не
применяется целиком — об этом ответ сообщает в `errors`.

### Остановка без обрыва вызовов

Остановка процесса обрывает идущие вызовы, поэтому перед ней вызывается
инструмент `prepare_shutdown`: он закрывает приём новых вызовов (`invoke_agent`,
`agent_run` в режиме пуска; доска, история, `wait_agent`, `agent_cancel` и
`health` работают как обычно), а `/health` начинает отдавать
`status = "draining"`. Дочерние вызовы идущих оркестраторов продолжают
приниматься. Ответ `{"status": "draining", ...}` перечисляет идущие вызовы —
повторяйте `prepare_shutdown` (или сразу задайте `wait_sec`, до 55 секунд) до
`status = "ready"` и только тогда останавливайте службу. Передумали —
`prepare_shutdown` с `abort = true` снова открывает приём.

## Добавление нового агента

Агент — каталог `agents/<имя>/`:

- `config.toml` — описание агента (обязателен);
- `prompt.md` — шаблон промпта на Tera с переменными из `input` (обязателен);
- `prompt.<вариант>.md` — другой вариант промпта, выбирается параметром
  `variant` при вызове (необязателен);
- `schema.json` — схема для проверки JSON-ответа; читается только когда этот
  файл указан в `response.schema_file`.

Пример `agents/summarizer/config.toml`:

```toml
name = "summarizer"
description = "Краткое изложение текста в JSON."
version = "0.1.0"
tags = ["example"]
kind = "prompt-template"      # prompt-template | agent-loop | orchestrator

[model]
provider = "deepseek"         # имя секции [providers.direct.<имя>], "claude-cli", "codex-cli" или "mock"
name = "deepseek-flash"
temperature = 0.2
max_tokens = 1024

[response]
format = "json"               # json | text
schema_file = "schema.json"   # необязательно; без поля файл схемы не читается

[input]
required = ["text"]
optional = ["max_points"]

[limits]
timeout_sec = 120

[cache]
enabled = true
ttl_sec = 3600
```

Пример `agents/summarizer/prompt.md`:

```
Изложи текст кратко. Верни JSON: {"points": ["...", "..."]}.
Пунктов не больше {{ max_points | default(value=5) }}.

Текст:
{{ text }}
```

Каталог агентов подхватывается на ходу примерно через 500 мс (при
`hot_reload = true`).

`kind`: `prompt-template` — один запрос без инструментов; `agent-loop` — цикл
с инструментами; `orchestrator` — агент, который сам вызывает других агентов.
Секция `[execution]` задаёт условия исполнения вызова (`allowed_tools`,
`disallowed_tools`, `permission_mode`, `cwd_template`, `mcp_config`,
`max_turns`, `extra_args`): claude-cli передаёт их ключами командной строки,
прямые провайдеры — набором инструментов в запросе к модели, а codex-cli
применяет только `extra_args` (об остальных полях служба предупреждает при
загрузке агента). Прежнее имя секции `[claude_cli]` продолжает
читаться как псевдоним. Ключ `allowed_roots` сужает файловые инструменты
`fs_*` этого агента своими корнями: они действуют ВМЕСТО общего
`[fs] allowed_roots` службы, а рабочий каталог вызова обязан лежать внутри
одного из них (без ключа действует общий список службы).
